# ПРОЄКТ (ВЛАСНА ТЕМА)

## Умова:

Розробити гібридну інформаційну систему, що поєднує алгоритми на основі правил та AI-модель для автоматизованої перевірки документів у сфері міжнародної логістики. Система повинна аналізувати супровідні документи водія (CMR, інвойси тощо), витягувати з них ключові дані за допомогою AI-моделі та виконувати їх автоматичне зіставлення з електронними митними даними.

## Опис проєкту

Міжнародна логістика та вантажні перевезення супроводжуються оформленням великої кількості супровідної документації. Ключовою проблемою галузі є необхідність постійної звірки фізичних паперових документів, які знаходяться у водія (міжнародна накладна CMR, комерційний інвойс), з електронними митними базами даних, такими як транзитна декларація RMPD. Будь-які невідповідності між цими даними можуть призвести до значних фінансових штрафів та затримок на кордоні. Даний проєкт являє собою гібридну програмну систему, яка автоматизує процес пошуку розбіжностей, усуваючи вплив людського фактора та значно прискорюючи роботу логістичних диспетчерів.

### Технічні характеристики

Джерела даних — це реальні митні декларації у форматі `HTML`, фотографії транспортних накладних (CMR) та комерційних інвойсів. Для комплаєнс-контролю використовуються локальні `JSON`-бази (GPS, ЄКМТ) та дані з офіційного порталу PUESC (PDF).

Pipeline обробки даних складається з 5 етапів: 
1) Детермінований парсинг `HTML` (RMPD);
2) Мультимодальний `OCR`-аналіз фотографій документів;
3) Нормалізація та алгоритмічна валідація даних;
4) Комплаєнс-перевірки (SENT, GPS, дозволи);
5) Візуалізація звіту для користувача.

Для `OCR` та складних логічних мікрозапитів використовується мультимодальна `LLM (Google Gemini 2.5 Flash)`. Для порівняння текстів — детермінований алгоритм Раткліффа-Обершельпа (`Fuzzy Matching`). Для пошуку товарних кодів — регулярні вирази (`RegEx`).

Система базується на правилах (`Rule-based Orchestrator`). Політика прийняття рішень щодо розбіжностей спирається на метрику схожості: 100% — Збіг, 80-99% — Жовта зона / Попередження, <80% — Критична помилка.

Графічний веб-інтерфейс, реалізований за допомогою фреймворку `Streamlit`, з підтримкою `Drag-and-Drop` мультизавантаження файлів та кольорового кодування результатів.

Час повного циклу обробки пакету документів складає 15–20 секунд.

`Accuracy threshold` встановлено на рівні 80% для `Fuzzy Matching`, що дозволяє системі бути стійкою до незначних опечаток `OCR` та артефактів на сканах документів.

### Архітектура та технологічний стек

Система побудована за принципом гібридної архітектури, що поєднує детерміновані алгоритми (строгі правила) та моделі штучного інтелекту. Використання виключно великих мовних моделей (`LLM`) для порівняння митних даних є ризикованим через їхню схильність до "галюцинацій" при виконанні точних текстових або математичних звірок. Тому в даному проєкті ШІ виступає виключно в ролі інструмента для зчитування складної графічної інформації, тоді як ядро прийняття рішень базується на строгому алгоритмічному коді, написаному мовою `Python`.

Для вилучення структурованих даних з `HTML`-файлів електронної декларації використовується бібліотека `BeautifulSoup4`. Обробка неструктурованих сканованих копій CMR та інвойсів здійснюється за допомогою мультимодальної моделі `Google Gemini 2.5 Flash`, яка дозволяє аналізувати кілька зображень одночасно у великому контекстному вікні. Алгоритмічне порівняння текстів реалізовано за допомогою вбудованого модуля `difflib`. Графічний інтерфейс користувача побудовано на базі фреймворку `Streamlit`, що дозволило об'єднати візуалізацію та виконання бекенд-логіки в єдиному середовищі.

### Методика роботи та ключові алгоритми

Процес обробки документів починається з детермінованого парсингу HTML-коду декларації RMPD. Система здійснює навігацію по `DOM`-дереву, вилучаючи реквізити сторін, дані про транспортні засоби та маршрути. Окремий алгоритм розбиває суцільні текстові блоки адрес на логічні складові (вулиця, індекс, місто, країна) для подальшого точного порівняння.

Паралельно з цим, модуль комп'ютерного зору відправляє фотографії CMR та інвойсів до `LLM`. Моделі задано строгий промпт, який вимагає повертати дані виключно у форматі `JSON` та категорично забороняє самовільний переклад власних назв. Це гарантує, що назви компаній та адреси будуть вилучені саме в тому вигляді, в якому вони написані в оригіналі, навіть якщо документи заповнені різними мовами.

Консолідація та перевірка даних відбувається у модулі валідатора. Для порівняння текстових значень застосовується алгоритм нечіткого порівняння Раткліффа-Обершельпа. Система розраховує коефіцієнт схожості для кожного поля і використовує концепцію жовтої зони довіри. Якщо схожість складає 100%, фіксується повний збіг. Якщо схожість знаходиться в межах від 80% до 99%, система видає попередження про можливу опечатку систем розпізнавання, запобігаючи хибному маркуванню критичної помилки.

Окрім базової звірки, система виконує складні аналітичні перевірки. Валідатор робить мікрозапити до ШІ для оцінки географічної доцільності транзитних маршрутів між пунктами пропуску та аналізує юридичну коректність заявлених правових підстав перевезення. Додатково реалізовано автоматизований комплаєнс-контроль: система на льоту завантажує актуальні нормативні акти з порталу PUESC, формує за допомогою регулярних виразів список ризикових кодів європейської системи SENT і порівнює їх з товарними кодами, знайденими в документах. Також проводиться звірка номерів телематичного обладнання (GPS) та дозволів ЄКМТ з локальними базами даних компанії у форматі JSON.

### Інтерфейс користувача та результати

Взаємодія з системою відбувається через мінімалістичний веб-інтерфейс. Користувач завантажує декларацію та фотографії документів за допомогою зручних зон перетягування, після чого ініціює перевірку. Завдяки оптимізації процес обробки займає близько 15-20 секунд.

Результати аналізу розподілені по логічних вкладках. Основний звіт про розбіжності використовує кольорове маркування: зелені блоки для підтверджених даних, жовті для попереджень про можливі неточності розпізнавання та червоні для критичних розбіжностей у документах або відсутності дозволів. Окрема вкладка демонструє результати перевірки товарів на належність до системи моніторингу SENT, сигналізуючи про необхідність додаткового митного оформлення ризикових вантажів.

### Запуск проєкту локально

Для запуску системи необхідно мати встановлений `Python` версії 3.10 або вище. Спочатку потрібно встановити необхідні залежності, виконавши команду `pip install streamlit beautifulsoup4 google-genai pillow PyPDF2 requests`.

Оскільки для розпізнавання зображень та логічних перевірок використовується `Google Gemini`, необхідно отримати безкоштовний `API` ключ у `Google AI Studio`. Цей ключ потрібно вставити у відповідні змінні `API_KEY` у файлах `ocr_by_api.py` та `validator.py`. Після цього застосунок запускається з терміналу командою `streamlit run app.py`, що автоматично відкриє інтерфейс системи у браузері за замовчуванням.
